# Новый эндпоинт «Календаря звонков»

## Зачем нужен фиксированный порядок

`spec/main.tsp` — источник истины для фронта и бэка. Фронт пишется по нему, не заглядывая
в код сервера. Если реализация уходит вперёд контракта, контракт начинает врать, и ошибка
всплывает не здесь, а на стороне фронта, где её дороже искать.

Отсюда порядок: **контракт → схема → реализация → тесты**. Каждый шаг опирается на
зафиксированный предыдущий, а не на догадку о нём.

## Шаг 1. Сверить контракт

Прочитай `spec/main.tsp` и найди нужную операцию в интерфейсах (`PublicEventTypes`, `PublicBookings`, `AdminEventTypes`, `AdminBookings`).

- **Эндпоинт есть, поведение совпадает с задачей** → ничего не меняешь, идёшь дальше.
- **Эндпоинта нет, либо задача меняет его поведение** (другой код ответа, новое поле в DTO,
  другая семантика) → **сначала правишь контракт**, потом код.
- **Контракт молчит о случае, который встретился при реализации** (не описано тело успешного
  ответа, не определено поведение при пустом параметре, не сказано, что отвечать на `start`
  вне окна записи) — это нормальная и частая ситуация. Дополни контракт, но помни: ты принимаешь
  решение за человека, поэтому оно должно быть видимым.
- **Задача противоречит действующему правилу контракта** — не выбирай молча, чему следовать.
  Останови работу и покажи противоречие: «в контракте правило N говорит X, задача требует Y».
  Решение принимает человек, потому что контракт — это договорённость, а не деталь реализации.

**Каждое изменение контракта попадает в финальный отчёт отдельным списком** — что изменил,
какой случай это закрывает и какое поведение выбрано. Договорённость, которую человек не заметил,
ничем не лучше её отсутствия: контракт читает ещё и тот, кто пишет фронт.

Переиспользуй уже описанные DTO. Параллельная структура с тем же смыслом
(`BookingDto` рядом с `Booking`) — это будущий рассинхрон фронта и бэка.

## Шаг 2. Схема БД

Нужны ли эндпоинту новые поля, таблицы или индексы? Если да — правь `server/schema.sql`
до реализации.

Таблиц две — `event_types` и `bookings`. Проверь, не покрыто ли требование существующими
ограничениями: exclusion-ограничение `bookings_no_overlap` (брони не пересекаются глобально),
`CHECK` на длины полей и длительность, `REFERENCES` без `CASCADE`. То, что держит схема,
код не предугадывает, а обрабатывает ошибку БД (`23P01` → `409 slot_unavailable`).
Устройство схемы и таблица SQLSTATE — в скилле `db-layer`.

Хранилищ два с одинаковым интерфейсом: `repositories/memory.js` и `repositories/postgres.js`.
**Новый метод репозитория пишется в обоих файлах сразу.** Тесты идут на памяти, поэтому
метод, забытый в `postgres.js`, они не заметят.

Живой базы в проекте сейчас нет: Postgres ни разу не поднимался, `schema.sql` существует только
файлом. Значит SQL нельзя проверить исполнением — тесты подтверждают логику на памяти, но не
корректность запроса. Пиши SQL с этой оговоркой и называй её в отчёте.

Механизма миграций тоже нет. Когда база появится, правку `schema.sql` придётся сопровождать
ручным `ALTER TABLE ...` — поэтому уже сейчас выноси такое изменение в отчёт отдельным пунктом.

## Шаг 3. Реализация

Раскладка кода в `server/` — единая для всех эндпоинтов:

```
server/
├── app.js                 createApp({ repositories, now, staticDir }) — CORS, json, роутеры,
│                          404 на неизвестный путь, единый обработчик ошибок
├── index.js               точка входа: выбор хранилища по DATABASE_URL, засев, listen
├── db.js                  создание пула pg
├── errors.js              HttpError и фабрики ошибок контракта
├── time.js                сетка слотов, окно записи, overlaps() — одна на всё приложение
├── routes/                public.routes.js, admin.routes.js — только HTTP: параметры, коды
├── services/              правила предметной области и валидация тела (validation.js)
├── repositories/          memory.js и postgres.js — одинаковый интерфейс
└── mappers/dto.js         доменный объект → тело ответа по контракту
```

Слой `services` остаётся, даже если у конкретного эндпоинта «нет логики»: как только правило
появится, его место уже определено, и не придётся переносить код между слоями задним числом.
Единообразие здесь важнее экономии одного файла.

`createApp` принимает репозитории и `now` аргументами. Это не церемония: репозитории позволяют
работать без Postgres, а `now` — тестам не зависеть от дня прогона (слоты только по будням).

Что важно независимо от слоёв:

- **camelCase в API, snake_case в БД.** Контракт отдаёт `eventTypeId`, `start`,
  `durationMinutes`; таблицы хранят `event_type_id`, `start_at`, `duration_minutes`.
  Строка БД → доменный объект — внутри `postgres.js`; доменный объект → тело ответа —
  только в `mappers/dto.js`. Разъехавшийся маппинг даёт молчаливые `undefined` в ответе.
- **Занятость — пересечение интервалов**, а не совпадение времени начала, и глобальная:
  бронь `[S, S+durB)` любого типа встречи пересекает искомый `[T, T+dur)`. Генерация слотов
  (`services/slots.js`) и проверка при вставке (`memory.js`) зовут **одну** функцию
  `overlaps()` из `time.js`; в Postgres ту же роль играет `bookings_no_overlap`.
- **Ошибки** — в формате `{ error: "machine_code", message: "русское описание" }`.
  `error` читает фронт, `message` читает человек.
- **Время — только UTC.** Таймзон в приложении нет: сетка 09:00–18:00 UTC по будням,
  окно 14 дней. Входящий момент обязан нести зону (`Z` или смещение) — `requireInstant`
  отвергает строку без неё, иначе `new Date` молча прочитал бы её в зоне сервера.
- **Числовые пределы и прочие константы** (максимальная длина поля, лимиты) не дублируй
  в схеме и в коде двумя независимыми значениями. Держи одно место — либо ограничение в БД,
  либо константу в коде. Если по делу нужны оба, назови это в отчёте: «лимит N задан в двух
  местах, при изменении править оба».

## Шаг 4. Тесты

Инструменты: **Vitest + supertest**.

Для каждого эндпоинта пишутся три группы:

1. **Happy path** — успешный сценарий с проверкой формы ответа: коды, все поля DTO из контракта.
2. **Ошибки** — каждый код ответа, указанный в контракте для этого эндпоинта (`400`, `404`,
   `409`), с проверкой значения `error`, а не только статуса.
3. **Граничные случаи** — там, где логика опирается на интервалы и время: слот впритык
   к концу рабочего дня, соседние непересекающиеся слоты, пересечение с бронью другого
   типа встречи, повторная запись на занятый слот, `start` мимо сетки или вне окна.

Приложение для теста собирает `buildApp()` из `server/tests/helpers/app.js`: настоящее
хранилище в памяти и зафиксированное `now` (понедельник, 07:00 UTC). Заглушек не заводи.

Тест на «форму ответа» стоит писать против контракта, а не против текущего кода: если код
отдаёт лишнее поле, тест должен это поймать, иначе фронт получит то, чего не ждёт.

Состав полей сверяй целиком — `Object.keys(body).sort()` против списка из контракта, как в
`public-api.test.js`. Так ловится не только пропавшее поле, но и лишнее, а для необязательных
полей (`notes`) — и то, что пустое значение не отдаётся вовсе.

## Шаг 5. Самопроверка перед отчётом

Прежде чем сказать «готово», проверь по списку — и допиши недостающее, а не упомяни в отчёте:

- [ ] Контракт и код описывают одно и то же: путь, метод, коды ответов, состав DTO.
- [ ] Все коды ответов из контракта реально возвращаются кодом и покрыты тестами.
- [ ] Новый метод репозитория есть и в `memory.js`, и в `postgres.js`.
- [ ] Ошибки идут через фабрики `errors.js`, а новый код ошибки сначала появился в контракте.
- [ ] Изменения контракта вынесены в отчёт отдельным списком (Шаг 1).
- [ ] Правка `schema.sql` сопровождается готовым `ALTER TABLE` (Шаг 2).
- [ ] Тесты прогнаны, зелёные, и `git diff` не содержит правок в тестовых файлах,
      сделанных ради того, чтобы тест позеленел.
- [ ] `npm run lint` зелёный. Правило линтера не отключается ради своего кода: если оно мешает,
      это повод назвать его человеку, а не дописать `eslint-disable`.

**Если тесты прогнать нельзя** (нет установленных зависимостей, нет базы) — не считай пункт
выполненным и не пиши «готово» без оговорки. Скажи прямо: тесты написаны, но не запускались,
причина такая-то, проверено тем-то (например, `node --check`). Невыполненный шаг, названный
вслух, стоит дёшево; невыполненный шаг, поданный как выполненный, стоит отладки на проде.

Пункт про `git diff` важен по той же причине: зелёный прогон означает «критерий выполнен»,
а не «поведение правильное». Подогнать тест под код — самый простой способ получить зелёный
прогон и самый дорогой в отладке потом.

## Правила контракта, которые легко потерять

Собраны здесь, потому что все они «невидимы» в коде отдельного обработчика и всплывают
только при чтении контракта целиком:

| Правило | Почему так |
|---|---|
| Занятость глобальная: пересекающееся время нельзя занять двумя бронями даже разных типов | Владелец календаря один — он не может быть на двух звонках сразу |
| `start` мимо сетки или вне окна → `400 validation_failed`, пересечение → `409 slot_unavailable` | Фронт на `409` перезагружает слоты, на `400` — нет: это ошибка запроса, а не гонка |
| Несуществующий тип встречи в `POST /bookings` → `404` раньше, чем `400` по `start` | Без типа неизвестна длительность, проверять `start` на сетку не на чем |
| Необязательное поле без значения не отдаётся, а не приходит `null` | Фронт типизирован по спеке и `null` не ждёт |
| Неизвестный путь → `404 not_found` телом `{ error, message }`, а не HTML Express | Клиент всегда разбирает JSON; общие ошибки перечислены в шапке `main.tsp` |
| `/admin/*` без авторизации | Авторизация вынесена ТЗ за скоуп; CORS здесь не граница безопасности |
| Бэк и фронт на разных origin в деве | Нужен явный CORS, иначе рабочий эндпоинт не доедет до SPA |

## Эталон

`POST /bookings` — эндпоинт, где сходятся все слои и все правила выше. Читай эти файлы как образец,
прежде чем писать свои: следовать готовому примеру надёжнее, чем восстанавливать конвенцию по описанию.

| Слой | Файл |
|---|---|
| Контракт | `spec/main.tsp` — `interface PublicBookings` |
| Роут | `server/routes/public.routes.js` |
| Сервис | `server/services/bookings.service.js` |
| Валидация тела | `server/services/validation.js` |
| Сетка и пересечение | `server/time.js` |
| Репозитории | `server/repositories/memory.js`, `server/repositories/postgres.js` |
| Маппер | `server/mappers/dto.js` — `toBookingDto` |
| Ошибки | `server/errors.js` |
| Тесты | `server/tests/public-api.test.js` — `describe('POST /bookings')` |
| Сборка для тестов | `server/tests/helpers/app.js` |

На что смотреть в эталоне:

- Роут не принимает решений: разбирает запрос, зовёт сервис, отдаёт код. Все ветки ошибок — в сервисе
  и хранилище.
- Порядок проверок в сервисе повторяет порядок кодов из контракта: форма тела → `404` → `400` по сетке →
  `409` от хранилища.
- Пересечение проверяет хранилище, а не сервис: в памяти — синхронно перед вставкой, в Postgres —
  ограничением. `SELECT` перед `INSERT` в сервисе оставил бы окно для гонки.
- Тест занятости создаёт бронь **другого** типа встречи — иначе глобальность занятости не проверена.
