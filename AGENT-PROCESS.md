# Агентный процесс в этом репозитории

Модуль 2 курса — не про новые функции приложения, а про то, как в проект встраивается
агент: он разбирает задачи, открывает pull request'ы и регулярно проверяет продакшен.
Здесь описано, как это устроено, как этим пользоваться и что из этого вышло.

Само приложение описано в [`README.md`](./README.md), решения по нему — в
[`PLAN.md`](./PLAN.md), очередь задач — в [`BACKLOG.md`](./BACKLOG.md).

## Как вызвать агента

Агент живёт в комментариях: пишете команду в issue или в комментарии к коду в pull
request — и он отвечает туда же.

| Команда | Что делает |
|---|---|
| `/oc explain this issue` | разбирает задачу и объясняет причину, ничего не меняя |
| `/oc fix <описание>` | правит код и открывает pull request |
| `/opencode …` | то же самое, полное имя команды |

Пример из жизни проекта — issue #3. Задача была заведена намеренно расплывчато, словами
постороннего пользователя: «Развернул приложение заново, зашёл — а в списке уже что-то
есть, хотя я ничего не добавлял». По `/oc explain this issue` агент нашёл причину сам и
указал на `seedIfEmpty` в `server/index.js` с номерами строк. Следующей командой
`/oc fix` он открыл PR #4.

Отвечает агент моделью `opencode/big-pickle` — единственной в OpenCode Zen, доступной
без привязанной карты; остальные (`claude-*`, `gemini-*`, `glm-*`, `deepseek-*`)
возвращают «No payment method».

## Workflow в репозитории

| Файл | Когда запускается | Права | Зачем |
|---|---|---|---|
| [`ci.yml`](.github/workflows/ci.yml) | push в `main`, любой pull request | `contents: read` | контракт, линтеры, 88 юнит-тестов, сборка фронта, e2e и дев-связка |
| [`opencode.yml`](.github/workflows/opencode.yml) | комментарий с `/oc` или `/opencode` | read + `id-token: write` | сам агент: разбор задач и правки кода |
| [`lighthouse-nightly.yml`](.github/workflows/lighthouse-nightly.yml) | cron `0 3 * * 1` и вручную | read + `issues: write` | еженедельный замер продакшена и разбор отчёта |
| [`release-please.yml`](.github/workflows/release-please.yml) | push в `main` | `contents: write`, `pull-requests: write` | релизный PR и changelog по conventional commits |
| [`hexlet-check.yml`](.github/workflows/hexlet-check.yml) | push | по умолчанию | проверка платформы, файл трогать нельзя |

## Что сделано для безопасности

**Агента вызывают только свои.** Репозиторий публичный: комментировать issue может кто
угодно, а каждый вызов агента тратит токены. Поэтому `opencode.yml` проверяет не только
текст команды, но и автора — `author_association` должен быть `OWNER`, `MEMBER` или
`COLLABORATOR`.

**Бот не будит бота.** Условие `github.event.comment.user.type != 'Bot'` отсекает
самозапуск: агент отвечает от имени GitHub App, и `/oc`, попавший в его собственный
ответ, нового прогона не вызовет.

**Триггер узкий.** Запуск только на `issue_comment` и `pull_request_review_comment` с
командой в теле — не на каждый комментарий подряд.

**Права минимальны и заданы явно.** У `ci` только чтение. У агента чтение плюс
`id-token`. `issues: write` есть лишь там, где агент обязан завести issue с отчётом —
без этого права он не находит способа это сделать и уходит искать учётные данные по
конфигам `gh`, на чём и виснет. Write-права на содержимое есть только у release-please.
Секции `permissions` прописаны в каждом workflow: без них действует умолчание
репозитория, а оно меняется одной галкой в настройках.

**Токен не остаётся в рабочей копии.** Во всех checkout'ах стоит
`persist-credentials: false`.

## Что сделано для контроля расходов

- **Лимит времени у каждой агентской джобы.** Без него зависший прогон работает до
  умолчания GitHub — шести часов. 30.08 два прогона висели 42 и 55 минут и были
  остановлены руками; успешные укладываются в 30 секунд для разбора и 5 минут для
  правки. Отсюда `timeout-minutes: 15` у агента и `20` у ночного замера.
- **Разбор отчёта не роняет замер.** Шаг агента в `lighthouse-nightly` помечен
  `continue-on-error: true`, а сам отчёт сохраняется артефактом раньше — сырые данные
  переживают любую ошибку в разборе.
- **Расписание раз в неделю, а не раз в сутки.** Производительность этого проекта
  меняется от правок, а не от календаря, и ежедневный прогон жёг бы минуты раннера
  впустую.
- **`ci` не дублируется.** Триггер `push` ограничен веткой `main`: с `branches: ['**']`
  каждый PR получал два одинаковых прогона — это было видно на PR #4.
- Где смотреть: вкладка **Actions**, прогоны сгруппированы по именам workflow выше.
  Отчёты Lighthouse лежат артефактами `lighthouse-<run_id>` со сроком хранения 30 дней,
  их разбор — в issue с заголовком «Lighthouse: отчёт за <дата>».

## Регулярная проверка продакшена

Ночью с воскресенья на понедельник workflow будит приложение (free-план Render усыпляет
контейнер после 15 минут простоя, и без пробуждения Lighthouse измерил бы холодный старт
контейнера, то есть тариф хостинга, а не приложение), снимает метрики, сохраняет отчёт
артефактом и просит агента завести issue с разбором: таблица по четырём категориям,
ключевые метрики, до пяти самых дорогих замечаний и раздел «Что делать» — с требованием
писать про правки в этом репозитории, а не общие советы, и отдельно отмечать, когда
виноват хостинг, а не код.

Отчёты за 30.08, 07.09 и 14.09 — issues #5, #11, #12.

Отдельная находка про сам GitHub: временный cron `*/15 * * * *` не дал **ни одного**
прогона за 100 минут при активном workflow в дефолтной ветке — восемь слотов подряд
пропущены. Частые расписания платформа прореживает, а точное время не гарантирует в
принципе. Работоспособность workflow проверялась через `workflow_dispatch`.

## Самооценка

**Решено с первого прохода.** Агент точно локализовал причину бага в issue #3
(`seedIfEmpty`), корректно исправил SEO-теги и `robots.txt` в PR #8, и регулярно строит
качественные отчёты по Lighthouse.

**Потребовали итераций — два случая.**

*Флаг `SEED_DEMO` (PR #4).* Агент сравнивал значение переменной со строкой нестрого;
через ревью сравнение запрещено и добавлены тесты. Сейчас в `server/seed.js` список
допустимых значений, а нераспознанное валит старт с понятным сообщением.

*Разделение бандла (PR #10).* Агент сделал ленивой в том числе главную страницу
`EventTypesPage`, что ухудшало LCP — inline-комментарием в ревью вернули статический
импорт. Ленивыми остались только страницы владельца и брони.

Задач, решённых с первого раза, больше — и это ожидаемо: они были поставлены как
**конкретный дефект** («нет meta description», «`robots.txt` отдаёт HTML»). Оба случая с
итерациями объединяет другое: задача формулировалась через **средство** («разделить
бандл», «спрятать за флаг»), а ценность лежала в **эффекте** («первая страница
открывается быстро», «в проде нет демо-записей»). Агент честно выполнял написанное, и
оба раза формально был прав: тесты зелёные, бандл разделён, флаг работает. Зелёный CI
такие расхождения не ловит — в первом случае не было теста на вариант написания
значения, во втором метрика вообще живёт снаружи кода.

Практический вывод для этого репозитория: если задача описана через средство, результат
смотрит человек — и до мержа, а не после.
